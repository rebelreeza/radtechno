Suppliers / Manufacturers

Physical inventory arrives. Odoo receives it via purchase order confirmation, updates on-hand quantities, then pushes updated availability to Shopify. This is the start of the inventory chain.

Airbyte pulls from Shopify API + Odoo Postgres (read-only user) every 15–60 min

Sync / ETL layer - one-way copy, read only from sources

ETL / Sync Tool

Shopify via native Airbyte connector (API). Odoo via Airbyte's Postgres connector against a read-only DB user - more reliable than Odoo's community Airbyte connector. Transforms into consistent schemas and loads into BigQuery. Never writes back to either source.

Tool options

Airbyte self-hosted - start here ($10-15/mo VM) Fivetran - paid, zero config, scale later

Why pull from both? Shopify has marketing attribution, abandoned carts, storefront data that never reaches Odoo. Odoo has cost of goods, PO history, financials Shopify never sees. You need both to get the full picture.

Loads into warehouse - historical, append-only, never modified

Data warehouse - analytical layer, read-only

BigQuery - Central Data Warehouse

The working assumption: business events from Shopify and Odoo accumulate here as read-only copies, optimized for analytical queries rather than live transactions. Dashboards, reports, and AI tools would read from here rather than hitting the operational systems directly.

orders

All orders across 40 stores. Store, creator, SKU, amount, channel, campaign attribution, date.

inventory_snapshots

Read copy from Odoo for trend analysis - not operational. Odoo owns live inventory; this is a snapshot for analytics only.

financials

Read copy from Odoo's accounting module for cross-store margin analysis. Odoo remains the system of record; this enables reporting without querying it directly.

customers

Unified identity across all stores. Multi-store buyers surfaced. LTV calculated.

products

All SKUs tagged with shared taxonomy - category, material, price tier, manufacturer.

campaigns

Campaign attribution data. Which campaigns drove which orders. UTM tracking, channel performance, commission tracking.

creators

Per-store performance. Revenue, returns, AOV, repeat rate. Cross-store comparisons.

purchase_orders

Read copy from Odoo's purchasing module. Useful for lead time trends and landed cost analysis without touching ERP directly.

All consumption is read-only - nothing writes back up the chain

Knowledge layer - unstructured docs, parallel to warehouse

Document Sources

SOPs, supplier contracts, creative briefs, past campaign reports, product specs, internal wikis. The institutional knowledge that lives in docs and emails rather than databases. Ingested on a schedule or triggered on upload.

Vector Store - Pinecone

Documents chunked and embedded. Semantic search retrieves the most relevant chunks before an AI generates a response. Handles questions the warehouse can't: "What did we agree with Supplier X on lead times?" or "What's the SOP for a drop going wrong?"

BigQuery + Pinecone feed the orchestration layer

AI Orchestration Layer

Routes each query to the right source - SQL against BigQuery for structured data questions, vector search against Pinecone for document and context questions. Both can be combined in a single response. Implemented as Claude tool-use, LangChain, or LlamaIndex. No additional cost - this is code, not a service.

AI & consumption layer - where value is delivered

CEO Dashboard

All 40 stores in one view. Revenue, inventory health, creator performance. Metabase (self-hosted, free) connected to BigQuery. No manual reports.

Structured Q&A

AI with warehouse read access - natural language translated to SQL. "Top 5 SKUs last week across all stores?" Answered in seconds. Works on numbers and events, not documents.

Knowledge Q&A (RAG)

AI retrieves relevant document chunks from the vector store before answering. For questions that live in docs, not data: SOPs, contracts, briefs, historical context. Different pipeline, same interface.

Automated Reports

Scheduled BigQuery queries that generate and email weekly summaries to the CEO and store managers. Nobody manually pulls these.

AI Agents / Alerts

Automated workflows reading warehouse data - reorder alerts when inventory drops below threshold, anomaly flags, campaign commission processing via n8n or Make.

Working principles - tentative

✓ Odoo is inventory source of truth ✓ Odoo pushes inventory → Shopify ✓ Shopify pushes orders → Odoo ✓ ETL pulls from both independently ✓ AI reads from BigQuery only ✓ BigQuery is append-only, historical ✗ BigQuery never pushes to Odoo or Shopify ✗ AI never writes to production systems ✗ Never run analytics against Odoo directly ✗ No Supabase needed - no custom apps yet

Why Odoo → Shopify for inventory

Shopify knows what's available to sell. Odoo knows what's actually in the warehouse. The working assumption is that Odoo should be the authoritative source - when a PO is confirmed, it pushes updated quantities to Shopify. Whether that's actually how it's configured today is one of the first things to verify.

Why pull from both in the ETL

Shopify has data Odoo never receives - abandoned carts, discount code attribution, storefront behavior, campaign referral UTMs. Odoo has data Shopify never sees - landed costs, PO history, accounting entries. The hypothesis is that you need both to get a complete picture, which is why pulling from each independently makes sense.

RAG vs. structured queries - two different pipelines

BigQuery answers questions about events and numbers - things that were recorded as structured data. RAG answers questions about knowledge - things that live in documents, contracts, SOPs, and briefs. An AI interface can route to either depending on the question, but they're built differently and solve different problems. The hypothesis is that WJ needs both: the warehouse for operational intelligence, the vector store for institutional knowledge retrieval.

Why BigQuery never feeds back up

The warehouse layer should be historical and analytical - a record of what happened, not a trigger for what happens next. If an AI agent needs to trigger a reorder in Odoo, the intent is for it to call Odoo's API directly, not route through the warehouse. That said, the exact boundaries depend on what we find in the audit.
